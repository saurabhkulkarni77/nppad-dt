WHAT WE LEARNED: TEACHING A COMPUTER TO SPOT A NUCLEAR ACCIDENT

We taught computer programs to look at one minute of sensor readings from a nuclear power plant and say which accident is happening. The plant is a computer simulation (PCTRAN, a well known reactor simulator), so accidents could be run safely and every sensor reading recorded. The best programs get the answer right almost every time, but only once the accident has actually started. Catching it in the first seconds, while the plant still looks normal, is beyond every program we tried. This page is the whole story, in plain words.

HOW THE BEST PROGRAM WORKS, IN SIX STEPS

STEP 1
READ THE SENSORS
88 sensor channels from the plant, read every 10 seconds. Eight extra "oracle" channels that would give the leak away directly are left out: no real sensor can see them, so using them would be cheating.
STEP 2
TAKE ONE MINUTE
Cut the readings into short windows lined up with the moment the accident starts. Lengths from 30 seconds to 10 minutes were tried; one minute is the main one.
STEP 3
TIDY THE NUMBERS
Squash extreme values and put every channel on the same scale, using rules fitted on the training runs only, then frozen.
STEP 4
LOOK FOR SHAPES
Thousands of fixed pattern matchers (a method called MultiRocket+HYDRA) turn the window into 50,752 numbers describing its shapes. This step is never trained; the patterns are fixed in advance.
STEP 5
SCORE THE 12 ACCIDENTS
One simple scoring layer gives each of the 12 accident types a score. The highest score is the answer; how far ahead it is becomes the confidence figure.
STEP 6
ANSWER AND REPORT
The answer, its confidence and the time are written to a log. The raw sensor window itself never leaves the plant computer.

WHICH ACCIDENTS GET MIXED UP

When a good program (here, Random Forest) is wrong, it is not wrong at random. Its mistakes follow the physics: similar accidents get confused with each other. This panel shows the pattern.

EXTENSION 1 OF 4: HARD PAIRS

Some pairs of accidents look almost identical to the sensors. This table scores each program on just the two accidents in a pair, at each window length, to see which pairs stay hard. A pair score counts only the test runs of those two accidents.

The hardest pair is LOCA and LOCAC: the same loss of coolant, at two different pipe locations (the hot leg and the cold leg). The steam generator pair and the inside/outside reactor building pair separate more easily, because sensors belonging to each loop say directly which loop is hurt.

EXTENSION 2 OF 4: ACCIDENTS THAT CREEP IN SLOWLY

The eight accidents were also run as slow ramps, creeping in while the plant changes power. The programs were only ever trained on sudden accidents. The scores drop a long way.

EXTENSION 3 OF 4: SPOTTING AN ACCIDENT IT NEVER LEARNED

One accident type was hidden from training completely. Can a program at least raise the alarm that something unknown is happening? For most programs the answer is no; only one uncertainty signal works as an alarm, and only at some window lengths.

CAN A CHATBOT READ THE PLANT?

We also tried something different: hand the same sensor windows to AI chatbots (language models) as plain text, and ask which accident it is, with no training at all. One chatbot did far better than the small models, but still far below the trained programs. Two well known chatbots could not be tested, for the practical reasons stated under the table.

HOW FAST IS THE PLANT COMPUTER VERSION?

Measured on one processor core with the study's own test program, under a memory budget of 512 MB, roughly what a small computer at the plant could offer. The plant version of the model scores exactly the same as the full study model: the shape matching step was rebuilt carefully and checked feature by feature against the original.

THE ANSWER, THE BACKUP, AND ONE HONEST LIMIT

The AI runs at the plant itself. An accident allows about a minute, so there is no time to send the readings off somewhere else and wait for an answer to come back. The main model was built and timed to run on a small computer at the plant, on the spot.

Only the answer is recorded. The system writes just the short event to its log: what happened, how confident, and when. About 150 bytes. The raw sensor window itself never leaves the plant computer.

If the main model breaks, a smaller one takes over. A checker keeps re-verifying the model's stored numbers. If they come out wrong, the system switches to a much smaller, simpler backup model (called LogReg+) instead of stopping. Its score is in the speed table on the left, and every event says which model made the call.

One honest limit. The confidence figure ranks the guesses; it is not a true probability. Read it as "how strongly the model prefers this answer", nothing more.
